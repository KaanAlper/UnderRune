# Shared battle leaderboard

The device hub becomes the public leaderboard. Chapter buttons remain as compact encounter navigation, preserving access to every card, preparation, practice, retry, theater and battle. No battle rules or source events are replaced.

Each completed full EngineBattle can publish a player-chosen display name and an immutable run: encounter, rules version, simulated active milliseconds (30 Hz; paused and hidden time excluded), cumulative positive party HP lost, participating characters with actual initial weapons and both armor slots, starting bag with duplicates, and items actually executed. Practice, defeat, aborted runs and local native-engine runs cannot submit. A run ID makes retry idempotent. Victory is captured exactly once. A voluntary publish action prevents accidental public names.

HP loss is the decrease in party HP clamped between zero and each character's max HP. Healing never subtracts past damage; heal-then-hit in one frame must still count. Knockout overflow and below-zero recovery do not count as additional damage. Tracking observes the shared HP array after battle setup and records item execution at scr_spell, without changing RNG, source working fields, events or numerical behavior. An unexpected replacement of the observed HP array makes the run ineligible rather than guessing.

Boards are scoped to one encounter and rules version. Default order: damage ascending, then duration ascending, then run ID. Fastest order reverses the two metrics. Filters: minimum/maximum damage and seconds, No item (zero executed items; a nonempty unused bag is allowed), No armor (all actual party members unarmored throughout the run), weapon, armor, starting-bag item and used item. All filters are combined before server-side ordering and pagination; never filter only the first loaded page. IDs are chapter-local. Detailed rows show gear by character, initial bag quantities and used quantities. Text is rendered with textContent. No synthetic scores appear as public results.

Use Supabase REST and Auth with a publishable browser key, anonymous sign-in on submission, public reads and authenticated owner-only inserts through a validated SQL RPC. No client secret or service-role key. Rows are immutable to clients. SQL validates the schema, bounded integers, encounter/rules identifiers, item/gear arrays, derived no-item/no-armor categories and name length; insert throttling and duplicate IDs are handled in the RPC. These are client-reported runs, not server-verified gameplay. The UI identifies that distinction. Deterministic replay verification is a separate future feature.

The deploy contains a public configuration JSON with URL and publishable key only. An absent configuration produces an honest unavailable state, working filters and retry; it does not claim local records are global. Network/auth errors preserve the finished run for an explicit retry, with timeout and duplicate-click guards. Publishing never blocks playing. The owner has no Supabase project yet; prepare migration and tests, then require their project URL and publishable key to activate shared storage. Do not fabricate credentials or publish a nonfunctional service as complete.

Visual direction: existing black/purple theater, lavender headings, pale numeric text, yellow keyboard focus, green challenge badges. The board is a compact score sheet with tabular numeric metrics and expandable equipment, rather than more boss cards. All filters have labels, work via native controls and keyboard, collapse gracefully on mobile and retain their values during loads. Keep stable controls while results update; cancel stale requests. No decorative animation is necessary.

Existing responsibilities stay where they are: chapter loading/error/retry and scene lifecycle in main.ts; chapter/boss cards in BossDeck; equipment persistence, validation and launch in PreparationPanel; input buffering/pause/audio in their existing hosts. New metric collection, API transport and leaderboard UI are separate modules. Existing chapter button labels and opener focus restoration remain compatible with current keyboard/browser flows.
